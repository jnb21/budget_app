Budget App on AWS

Phase 1: one server and no load balancer yet. Route 53 points your domain at CloudFront, CloudFront serves the React app from S3 and sends /api/* to an EC2 server, and the AI agents run on that server and call Amazon Bedrock.

Static app: browser → CloudFront → S3 API: browser → CloudFront → EC2 Domain shown as budget.example.com (placeholder)

Three changes to the sketch

1 · ROUTE 53

DNS only, then out of the way

Route 53 answers one question: where is budget.example.com? It returns CloudFront's address (an alias record), and from then on the browser talks to CloudFront directly. Requests never pass through Route 53.

2 · CLOUDFRONT

Two branches, not one chain

CloudFront splits requests by path. Loading the app (/, /assets/*) goes to S3 and never touches the server. Saving a transaction (/api/*) goes to EC2 and never touches S3. One domain for both, so the login cookie works and there's no CORS, exactly like the Vite proxy in development.

3 · THE AI

Answers come back two ways

Chat: the agent runs inside the API request and streams its answer back. Background work, like auto-categorizing: the API doesn't wait. A worker does the job and writes the result to Postgres, and the screen shows it on the next load. Postgres was missing from the sketch; it's where those answers land.

The architecture

How an AI answer gets back to the screen

Both paths use the same agent code in backend/app/agent/, and its tools call services, never the database. So the AI gets the same rules, the same per-user filtering and the same row-level security as a click in the app.

Settings that make it work

CloudFront behaviors

  • /api/* and /health → EC2 origin, cache policy CachingDisabled, origin request policy AllViewerExceptHostHeader (cookies, query strings and headers reach the API).
  • Default /* → S3 with Origin Access Control; the bucket stays private.
  • assets/* files have hashed names: cache for a year. index.html: no-cache, so a deploy shows up at once.

Lock the server to CloudFront

  • Security group: port 443 only from the AWS-managed prefix list com.amazonaws.global.cloudfront.origin-facing.
  • CloudFront adds a secret header (say X-Origin-Verify); Caddy refuses requests without it. The prefix list alone also admits other people's CloudFront distributions.
  • CloudFront needs a hostname for the origin, not an IP: an Elastic IP plus a record like origin.budget.example.com, with Caddy's own certificate for that name.
Gotcha

Page URLs like /dashboard

S3 has no file called dashboard. The usual fix, a custom error page that serves index.html on 403/404, applies to the whole distribution, so the API's real 404s ("transaction not found") would come back as the HTML page. Use a small CloudFront Function on the S3 behavior instead: any path without a file extension becomes /index.html.

Gotcha

Rate limits need the real visitor IP

Behind CloudFront, every request reaches the server from a CloudFront address, so the per-IP buckets for login and sign-up would lump strangers together. Add the CloudFront-Viewer-Address header (visitor IP:port) to the origin request policy and have the app read the IP from it. That's safe only because nothing but CloudFront can reach the server.

Gotcha

CloudFront waits 30 seconds

The default origin response timeout is 30 seconds (adjustable up to 60). An agent loop with several tool calls can take longer. Stream chat answers so bytes keep flowing, cap the loop's turns, and send anything slow to the worker.

Secrets and access

  • The EC2 instance role grants Bedrock, SSM Parameter Store, the backup bucket and CloudWatch. No keys on disk.
  • The owner (migration) password is only given to the migration step; the running app gets the app login only, as the README already requires.
  • COOKIE_SECURE=true. Pick a region where Bedrock offers the model you want; the CloudFront certificate always lives in us-east-1.

Postgres on the same server, for now

Cheapest, and the same Compose file you run locally. The cost is that the server is a single point of failure for your data too, so back it up from day one: nightly pg_dump to the backups bucket, plus daily EBS snapshots (Data Lifecycle Manager). Test a restore once.

Cost guard

Set an AWS Budgets alert before launching anything. Bedrock bills per token, so also cap the agent: turns per question and questions per user per day, with the same token buckets the API already uses.

Deploying a change

  1. GitHub Actions signs in to AWS with an OIDC role: no AWS keys stored in GitHub.
  2. Frontend: npm run build, aws s3 sync dist/ to the site bucket, then invalidate /index.html only.
  3. Backend: build the Docker image and push it to ECR.
  4. On the server (SSM Run Command, no SSH): run python -m app.migrate once with the owner login, then docker compose pull && docker compose up -d for the API and worker.

  • Backups, alarms, a budget alert.

Phase 2 · two servers

When downtime or load starts to matter
  • Postgres moves to RDS first: servers that come and go can't hold the data.
  • An Application Load Balancer with an Auto Scaling group of two becomes CloudFront's origin.
  • Rate-limit buckets live in memory per server, so move them to a shared store (a Postgres table or ElastiCache), or add AWS WAF rate rules on CloudFront.
  • The jobs table keeps working: SKIP LOCKED lets workers on both servers share it.
